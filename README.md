# Mandelbrot Set

在浏览器里实时探索 Mandelbrot 集：从全貌一直放大到 10^300 倍以上，所有计算都在本机完成。

- TypeScript + Vite 的单页静态站点，没有前端框架、服务端或分形运行时依赖。
- 任意深度的精确坐标（BigInt 定点数），深层使用扰动与 BLA 加速，多个 Worker 并行渐进渲染。
- 内部区域有严格的数学证明，不靠近似阈值；配色复刻维基百科上的经典动画 [`Mandelbrot_sequence_new.gif`](https://en.wikipedia.org/wiki/Mandelbrot_set#/media/File:Mandelbrot_sequence_new.gif)，并用距离估计勾勒边界；另有一套从 Maths Town 缩放视频逐帧实测的鲜艳配色，可随时切换。
- 当前视图写入 URL，可直接分享；右上角的分享按钮还能生成短链接（is.gd）。

需要支持 BigInt、模块 Worker 和 Pointer Events 的现代浏览器。

## 快速开始

```sh
npm install
npm run dev        # http://127.0.0.1:59472/
```

用 VS Code 打开项目后，也可以选择「dev」配置按 F5 启动。端口在 `package.json` 中配置，启动前请先停止已在运行的开发服务器。

构建与预览：

```sh
npm run build
npm run preview
```

把 `dist/` 部署到任意静态托管服务即可。页面最好带上 `Cross-Origin-Opener-Policy: same-origin` 和 `Cross-Origin-Embedder-Policy: require-corp` 两个响应头（开发服务器和 `vercel.json` 已经配置）：有了它们，Worker 可以共享同一份参考表（见“参考轨道”）；没有时仍能正常运行，只是每个 Worker 各存一份。

- 放大倍率相对于当前窗口的初始视图，极大时用科学计数法。
- 屏幕宽度不超过 640px 时，信息栏占满底部，Reset 和缩放按钮移到它的上方。

**视图对话框**：点击 Re、Im 或倍率中的任意一项，都会打开同一个对话框，显示完整的实部、虚部和倍率。

- **Copy** 复制这三个值，与信息栏的复制按钮相同。
- 三个值都可以修改，点 **Apply**（或按 Enter）跳到对应的位置和倍率。没改动的值保持原有的全部精度，不会被显示的位数截断。
- 坐标可以写成 `-0.75` 或 `1.2e-5`，粘贴时的空格、换行和 `−` 号会被自动处理；范围为 −4 到 4。
- 倍率可以写成 `250`、`2.5e12`，或信息栏显示的 `1.84×10^8` 格式；最大到 `1e18000`，过小时停在与滚轮相同的缩小极限。
- 有任何一个值无效时，对应输入框下方会给出提示，焦点移到第一个无效的输入框，视图不变。
- 点对话框外的空白处、右上角的关闭按钮或按 Esc 关闭对话框，不做任何改动。

**分享链接**：缩放和平移会把视图写入地址栏的 hash（`#re=…&im=…&zoom=…`），打开链接即还原到相同的中心和倍率。使用鲜艳配色时还会带上 `&palette=vivid`，打开链接看到的是同样的颜色。

- 坐标保留到比一个屏幕像素还细 3 位的精度，任意深度都能精确还原。
- 缩小后精度不丢：坐标按到过的最深一级所需的位数写出（链接、复制按钮、视图对话框和信息栏都一样）。所以放大找到有趣的位置后再缩小，甚至在对话框里把 Zoom 改回 1，发出去的链接仍带着那个深处的全部位数，对方按放大按钮放大回去，会精确回到同一处。打开链接或在对话框里输入坐标时，给出的每一位都会保留，转发链接时位数既不丢失也不增长；按 Reset 或打开别的链接后重新计算。
- 倍率相对于打开者窗口的初始视图，不同大小的窗口看到相同的取景。
- 用 `replaceState` 更新，不会在浏览记录里留下每一步；手动修改 hash 或前进、后退会跳转到对应视图，无效的 hash 会被忽略。
- 倍率超过 `1e18000` 的链接也被视为无效：深度越大，坐标需要的精度越高，过大的值会让页面尝试分配数 GB 内存。

**分享对话框**：右上角的分享按钮打开一个对话框，给出当前视图的短链接和完整链接，各有一个复制按钮。

- 完整链接是当前地址加上 hash，立即生成，不依赖任何外部服务。打开对话框时会先把地址栏同步到最新视图，不必等 hash 的延迟写入。链接不带查询参数：`?cpu` 这类本机调试开关和来源追踪参数不会传给对方。
- 短链接由 [is.gd](https://is.gd/) 生成。站点是纯静态的，由浏览器直接调用 is.gd：它的接口允许跨域（`Access-Control-Allow-Origin: *`），不需要密钥，客户端代码里也没有任何密钥。请求用表单编码的 POST，属于简单跨域请求，没有预检。
- 只在打开对话框时请求一次。同一个链接在页面内缓存，再次打开不重复请求（is.gd 的链接是永久的，官方也要求缓存）。请求超过 8 秒没有回应就放弃。
- is.gd 按 IP 限流（每小时 200 次），每位访客用的是自己的额度。收到限流错误后 1 分钟内不再请求。
- 以下情况不显示短链接，提示改用完整链接：
  - 链接超过 5,000 字符（is.gd 的上限）。这时不会发出请求。大约在倍率 10^2400 以上，或坐标带着更深处的位数时出现。
  - 本机或局域网地址（`localhost`、`127.0.0.1`、`*.local`、`192.168.x.x` 等，例如开发服务器）。is.gd 会拒绝这类地址，别人也打不开，所以不发请求，只提示短链接在发布后的站点上才能用。
  - 被限流，或 is.gd 拒绝该地址。
  - 网络不通、超时或服务故障。失败的结果不缓存，重新打开对话框会再试一次。
- 生成短链接会把完整地址发给 is.gd，适用它的[使用条款](https://is.gd/terms.php)：链接不能删除或修改，is.gd 也不保证服务长期可用。
- 与视图对话框一样，标题和底部按钮固定，只有中间部分滚动。点进链接框会全选内容，方便手动复制；在已选中的框里再点一次则放置光标，可以只选一部分。窄屏（480px 以下）时，复制提示单独占一行；按钮放不下时上下排列。旋转屏幕或调整窗口时，链接框会重新按内容调整高度。打开时快捷键不生效，按 Esc、点关闭按钮或对话框外的空白处关闭。

画布按完整的 `devicePixelRatio` 绘制，静止画面与物理像素 1:1。

## 工作原理

### 坐标与精度

视图中心用 BigInt 二进制定点数保存，精度随深度按 64 位递增，并保留至少 128 个超过一个像素所需的保护位。缩放尺度保存为以 2 为底的对数。因此高精度坐标从不整体转换成普通浮点数，极小的尺度也不会下溢。

### 迭代路径

| 深度（每 CSS 像素的尺度） | 方法 |
| --- | --- |
| 大于 2^-24 | 普通双精度直接迭代 |
| 2^-24 至 2^-900 | 围绕参考轨道的扰动，配合 BLA 跳步 |
| 小于 2^-900 | 同上，δ 与系数带独立的二进制指数；δ 回到双精度范围后改用双精度 |

**为什么 2^-24 就改用扰动**：普通双精度直接迭代时，舍入误差与 |z| 同量级（约为 1）；扰动的舍入误差只与很小的 |δ| 同量级。与 BigInt 逐像素比较细丝很多的视图，统计逃逸次数相差超过半次的像素：

| 深度（每像素） | 普通双精度 | 扰动 |
| --- | --- | --- |
| 2^-14 | 与扰动相当 | — |
| 2^-22 | 0.14–0.45% | 0.03–0.13% |
| 2^-26 | 0.2–1.5% | 0.02–0.2% |
| 2^-30 | 0.7–5.6% | 0.02–0.6% |
| 2^-34 | 3–7%，最多 118 个内外判定出错 | 0.03–0.3% |

- 以前到 2^-38 才改用扰动。现在 2^-24 至 2^-38 之间（1024 CSS 像素宽的窗口约 10^5–10^10 倍）的完整渲染慢 1.3–2.2 倍。
- 结果更准后，未定像素少了，预算有时也不必提得那么高：细丝视图在这一范围内最终预算从 98304–131072 降到 24576。

**浅层**：同一行的像素三路交错推进。单条轨道的每次迭代都要等上一次的结果，交错独立的轨道能让浮点单元保持忙碌，速度约为逐像素的 2 倍。每条轨道的运算与逐像素版本完全相同，结果逐位一致。

**参考轨道**：0 号 Worker 在视图中心用 BigInt 计算一条高精度轨道，以紧凑的类型数组经主线程转发给其余 Worker，各 Worker 据此构建自己的 BLA 表。

页面跨源隔离（`crossOriginIsolated`，需要上面部署一节的两个响应头）时，BLA 表也共享：0 号 Worker 算完轨道后先把它发给主线程（GPU 只要轨道），再在 `SharedArrayBuffer` 里建好全部 BLA 表发出，主线程转给其余 Worker。共享内存在线程间传递不复制，所以其余 Worker 不再各建一份，只等这一份。

- 参考轨道在一定范围内跨平移和缩放复用；参考点离视图中心超过 2^24 个 CSS 像素时重新计算，避免像素差异被浮点精度吞没。
- 正在计算的轨道若仍被新请求需要，会继续计算，不会因连续缩放反复重启。
- BLA 表都存成平铺的类型数组，2^-800 以下另有一份扩展指数的表（每块 7 个双精度数：A、B 各自的实部、虚部、指数，加上 log2 半径）。扩展指数的表原来是 BLA 对象，每块带两个 Extended 对象和若干装箱的双精度数。改成数组后，2^-1200、20 万步的参考表在每个 Worker 里每步从约 812 字节降到约 312 字节，计算结果逐位不变。不共享时每个 Worker 各存一份，内存估算允许的 Worker 数相应增加：例如 2^-1200 的默认预算（约 4 万步）原来只能开 6 个，现在可以开满 8 个。
- 扩展指数的路径也不再为轨道另建一份 Extended 对象，直接读轨道的类型数组，每步再少约 56 字节。参考表从此只由类型数组组成，可以整份放进共享内存。
- 共享参考表时，内存只有一份，不再按参考轨道长度减少 Worker。`-1.75`、`10^320`（纯 CPU，预算升到 565248）在 Apple M1 Max 上：不共享时只能用 1 个 Worker，13.2 s；共享时 8 个 Worker，3.3 s。在 Node 里用 8 个 Worker、52 万步渲染 320×200，各自建表时进程内存峰值约 5 GB，共享时约 1 GB。

**扰动**：每个像素以 z = Z + δ 跟踪自己与参考轨道 Z 的差：

```text
δ′ = (2Z + δ)·δ + δc
```

这种写法比展开的 `2Zδ + δ² + δc` 少两次乘法，依赖链也更短；舍入误差仍在内部证明使用的误差界之内。

- 当 |z| < |δ| 时把 δ 换回参考轨道起点（rebasing），参考轨道走到尽头时也一样。
- 检测到严重抵消（毛刺）时，该像素回退到 BigInt 直接迭代。

**BLA**（双变量线性近似）：在 |δ| < 2^-40·|2Z| 时略去 δ²，把多次迭代合并成一次线性映射 `δ ← A·δ + B·δc`。

- 单步引入的相对误差最多 2^-40，相当于把采样点移动远小于一个像素的距离。但在很长的块里，以及在弱排斥周期旁徘徊上千步的轨道（海马谷）上，这些误差会累积并被放大。
- **为什么从 2^-36 收紧到 2^-40**：逐像素与 BigInt 比较，统计逃逸次数相差超过半次的像素：

  | 视图 | 2^-36 | 2^-40 | 2^-44 | 不用 BLA（双精度本身的下限） |
  | --- | --- | --- | --- | --- |
  | 海马谷 `1.9×10^12`（640×257，预算 2560） | 1172（另有 238 个内外判定错误） | 220（66） | 220（66） | 220（66） |
  | 海马谷深处 `10^25`（240×150，预算 57344） | 412 | 233 | 152 | 149 |

  - 2^-40 消除了前一个视图里 BLA 带来的全部误差，后一个视图里约三分之二。代价是深层视图的采样时间最多多约 13%（10^25 为 +13%，10^314 为 +12%，10^290 不变）。
  - 2^-44 可以降到双精度本身的下限，但采样时间最多多 27%。
  - 剩下的误差是双精度扰动本身的极限：这些轨道在排斥周期旁把舍入误差放大约 10^13 倍，只有更高精度才算得准。
- 表按层存成 `Float64Array`，先用第 1 层半径快速排除，省去大多数查表。
- 只覆盖一步的块不值得用：它跳不过任何迭代，还舍掉了 δ²。这种位置直接做精确单步。

**普通单步的快速路径**：典型深层视图中 80–99% 的迭代是既不能用 BLA、也不需要任何记账的普通单步。它们走一条精简的内循环，只在需要时才交给通用代码：

- 至少两步的 BLA 块可能适用；
- 逃逸、出现毛刺或 |z| 极小；
- 周期跟踪确实要处理：出现新的最小值，或此刻可以尝试内部证明。

判断条件与通用代码完全相同。轨道在抛物点或排斥点附近徘徊时，|z| 会连续成千上万步落在跟踪范围内却什么也不用做，这些步骤也都留在快速路径里。

### 内部区域的证明

内部像素永远不逃逸，没有捷径就会把整个迭代预算跑满。下面的证明都只会得出“在集合内部”的结论，而且是带舍入误差界的严格包含证明，所以逃逸像素的结果不受影响。

**圆盘包含**：轨道回到此前的近零点附近时，以回归间隔 P 为候选周期，跟踪一个圆盘在 P 步后的像。

- 每步按 `|f(w) − f(z)| ≤ r(2|z| + r)` 并计入舍入误差界，同时尝试四种初始半径。
- 证明只需要上界。只出现在舍入项里的 |Z|、|δ| 用 √2·max(|x|, |y|)；在半径递推里起乘法作用的 |z| 用 √(x² + y² + 10^-280)。两者在任何深度都不会因下溢而偏小，也避开了在 V8 中慢一个数量级的 `Math.hypot`。
- 若圆盘的像落回圆盘内，`f^P` 把它映入自身，轨道永不逃逸。
- 证明的尝试次数和步数都有上限，单个像素的工作量最多增加一倍。

**吸引周期**：有些内部区域收敛极慢。例如放大约 4.17×10^13 倍处的周期 844 分支，轨道每绕一圈只向周期点靠近约 12%，要几万次迭代才出现足够接近的回归。因此深层路径在较粗略的回归时就尝试证明：

1. 用牛顿法直接求解 `f^P(w) = w` 的周期点（二次收敛）。
2. 在周期点周围用同样的圆盘检查证明 `f^P` 把圆盘映入自身。由 Schwarz 引理，这说明存在吸引周期。
3. `z² + c` 的吸引周期必然吸引唯一的临界点 0（Fatou），所以 0 的轨道有界，像素在集合内部，无需等轨道自己收敛过去。

牛顿迭代收敛到排斥周期（|λ| ≥ 1）时放弃。逃逸轨道也常经过排斥周期附近，所以第 k 次失败后要等 4P·2^k 步才再试。

**相邻像素的提示**：相邻的内部像素属于同一个分支，周期相同，周期点随 c 连续移动。所以一个像素被证明后，下一个像素先以它的周期点为初值做同样的证明（至多 4 圈），成功则完全不必迭代自己的轨道。

- 证明对任何初值都成立，失败也不改变后续计算，所以结果与像素的处理顺序无关。
- 证明出的周期点会先换算成真正的最小周期再交给下一个像素。浅层的行计算每 32 步才比较一次，检测到的往往是周期的若干倍，例如周期 3 被检测成 96。
- 提示在某个视图里多半失败时（被证明的像素零散地夹在外部像素之间），只每 16 次机会试一次。

**浅层与扩展指数路径**：

- 浅层的三路交错行计算同样使用吸引周期证明和相邻提示：在每 32 步一次的比较中，轨道回到保存点的 1/32 以内就尝试。
- 牛顿迭代收敛到不吸引的周期，或者收敛了却仍无法证明时，这个像素以后不再尝试。在抛物点附近徘徊的轨道每次都会找到同一个周期。
- 例如单线程按行计算时，1/3 分支根部附近快约 27 倍，2/5 分支根部附近快约 39 倍。在 13/30 分支根部这类几乎全是抛物型难像素的视图，逃逸前要数万次迭代的外部像素和极难收敛的内部像素混在一起，证明几乎都不成立，计算时间约多 3–6%，但未定像素少约四分之一。
- 2^-900 以下的扩展指数路径同样有圆盘包含、吸引周期证明和相邻提示，半径以 log2 记录，不会下溢；log2 运算本身的舍入也在最终比较里留出余量。它与普通指数路径有几处不同：
  - **BLA 步之后也跟踪回归**：深入小芒德布罗特集时，位于其中心附近的参考轨道每圈都回到接近 0 的地方（周期 250 的小芒德布罗特集约在 2^-700），而 δ 比 Z 还小得多，BLA 块会直接跨过这些回归。只看单步的话，内部像素永远等不到证明，一直跑满预算。
  - **只对近零基点放宽回退**：靠近 c = -2 或 c = i 时，轨道会在 |z| ≈ 1–2 的排斥周期附近长时间徘徊，那里的证明必然失败。失败后的指数回退只约束基点不比失败处小 2^10 以上的尝试，不会耽误后面接近 0 的回归。
  - **近零基点的证明额度按迭代数放宽**：基点小于 2^-10 时，证明的工作量可以达到迭代数的 1/8，而不只是循环步数；BLA 让每圈只剩寥寥几步，只按步数计要等几十圈才轮得到证明。放宽到 1/4 能多证明少量边缘像素，但在证明总是失败的视图（分支根部、尖点附近）会慢到约 3 倍。
  - **牛顿法的圈数受剩余额度限制**：扩展指数的每一步都和循环步一样贵，长周期上十圈失败的牛顿迭代会远超像素本身的工作量。
  - 对周期 250 和 400 的小芒德布罗特集，内部像素原来全部跑满预算，现在全部得到证明，内部视图快 3–5 倍；纯外部视图和证明不成立的视图耗时与原来相当（最多约 1.5 倍）。
- **扩展指数路径中的双精度段**：真正超出双精度范围的通常只有像素相对参考点的偏移 δc（10^300 倍时约 2^-1000）。逐像素迭代的 δ 在开头的 BLA 跳步之后，或者换回参考轨道起点之后，大多回到 2^-500 以上，|z| 也一样。这时扩展指数路径改用普通双精度推进，做法与普通指数路径的快速循环相同。原来每一步都要构造对象、做规范化，还要算 log2 和 hypot，一步比普通指数路径贵约 10 倍：
  - **单步可以略去 δc**：此时 |δc| < 2^-64 |δ′|，对 δ′ 的影响比它自身的舍入还小。δ′ 若会小于 2^-500，这一步交回扩展指数路径，带着 δc 计算。
  - **BLA 块也用双精度**：块里的 B·δc 先把 δc 乘以 2^600 再算，最后乘回 2^-600。缩放是精确的，因为下溢而丢掉的部分小于 2^-640。结果会溢出的块交回扩展指数路径。
  - **何时离开快速循环**：与普通指数路径的快速循环一样，凡是一般路径要做迭代以外的事，就离开快速循环：逃逸、接近毛刺界、超出范围、基点重置，或者这一步是证明记账要处理的回归。判断时为一般路径的 log2 比较留了余量。
  - **证明的逐步跟踪也可以用双精度**：半径在 [2^-900, 2^900] 内时，按普通指数路径的方式累计舍入误差，再加上略去的 |δc|；每次更新都向上舍入，最后一步与最终比较仍由一般路径完成。
  - **提前放弃无望的证明**：半径到 1 以后只会变大，因为 r(2|z| + r) ≥ r²。四个半径都超过最终比较允许的值后，这次证明不可能成立，不再跑完余下的周期。逃逸像素经过回归时的证明常常几十步内半径就超过 2^1000，以前每次都要用扩展指数跑完整整一个周期。这样的半径记作无穷大，所以剩下的半径仍可以用双精度跟踪。
  - **效果**：在 Mac mini 上，同一条缩放路径 240×150 采样的结果（参考轨道另计）：

    | 放大倍数 | 原来 | 现在 | 加速 |
    | --- | --- | --- | --- |
    | 1e268（仍在普通指数路径） | 0.33 s | 0.33 s | — |
    | 1e275 | 3.1 s | 0.41 s | 7.6× |
    | 1e290 | 2.9 s | 0.65 s | 4.5× |
    | 3.3e314 | 6.7 s | 0.64 s | 10.6× |

    逃逸值与原来的差异和原来自身的误差同一量级：两者不同的像素，与 BigInt 的偏差中位数都在 0.003–0.007 次迭代。这些都是对舍入极敏感的混沌像素。内部判定没有一处不同。
  - **仍然较慢的情况**：深处小芒德布罗特集中心附近的内部像素，轨道每圈回到 2^-1000 以内，证明半径也在这个量级，只能用扩展指数计算，速度与原来相同。

### 渲染流程

**渐进阶段**：每次渲染按 8、4、2、1 像素的步长分四个阶段补全细节。

- 每个 Worker 在各阶段负责固定的 32 像素分块，分散在整个画布上；各阶段都按离画布中心的距离由近到远计算，所以人们最先看的中心最先变清晰，补算未定像素时也一样。顺序不影响结果。
- 粗阶段在每块左上像素中心采样，所以每个粗采样都恰好是一个最终像素，更细的阶段直接沿用而不重算。最终图像与逐像素计算完全相同，总计算量少约 25%。
- 粗采样以采样像素为中心绘制，细化时画面不会来回移动。

**缩放预览**：缩放时立即变换显示已有图像，新渲染以旧图像的投影作为预览。比投影更粗的阶段仍会计算（统计用于迭代预算），但不覆盖更清晰的预览，避免画面在清晰与模糊之间来回跳。

**上传与复用**：

- Worker 约每 16 ms 批量发送分块，主线程写入 CPU 暂存缓冲，每帧只向画布上传一次。
- 同倍率平移时，复用重叠区域已完成的像素，只计算新露出和尚未完成的部分。
- 迟到的低分辨率分块不会覆盖已完成的高分辨率像素。

**调度与取消**：

- 单独一次变化（一格滚轮、开始拖拽）立即开始渲染。连续变化时，上一轮显示出粗阶段且已过 180 ms 才重新开始。
- 变化停止后再完整渲染：等待时间是 60 ms，或最后两次变化间隔的 2 倍（最多 500 ms）。
  - 原来固定为 60 ms。GPU 繁忙时会拖慢动画帧，按住缩放时，两次变化之间常常超过 60 ms，于是被当作“已经停下”，每帧都重新开始渲染，放大过程中一轮也完成不了。
- GPU 模式下，变化过程中的渲染只是预览（见“GPU 渲染”）；CPU 模式的各阶段本来就逐步显示，不受影响。
- Worker 每计算约 8 ms 让出一次以处理新消息。这里用自发的 `MessageChannel` 消息而不是 `setTimeout(0)`，因为后者嵌套后会被限制为至少 4 ms。旧任务的结果不会覆盖新视图。
- Worker 最多 8 个，通常为页面保留一个逻辑核心；小区域会减少线程数，不共享参考表时极长的参考轨道也会。

**同一视图重新渲染时保留质量**：提高预算后，同一视图会在新画布上重新渲染。这时每个像素保留原来的质量档（至少为 2），所以已经显示的 2 像素阶段不会再被粗阶段盖成模糊的。

### GPU 渲染

浏览器支持 WebGPU、GPU 通过启动自检，并且视图不深于每像素 2^-90（约 10^27 倍）时，由 GPU 计算各像素，Worker 只精确计算 GPU 定不下来的少数像素。其他情况下仍是上面的 CPU 渐进渲染。

**何时用 GPU**：

- 默认开启，不需要参数。页面地址带 `?cpu` 时只用 Worker，便于对比。原来开启 GPU 用的 `?gpu` 仍可使用，但已不需要。
- 浏览器支持 WebGPU 时，第一次渲染会等 GPU 初始化完成（最多 2 秒），而不是先交给 Worker、再整个丢掉重来。不支持 WebGPU 的浏览器不等待，直接由 Worker 渲染。
- 以下情况改由 Worker 渲染：
  - 没有 WebGPU，或拿不到适配器。
  - 适配器是软件实现（`isFallbackAdapter`），它会比 Worker 还慢。
  - 申请设备或编译着色器失败。
  - 2 秒内初始化没有完成。这时第一次渲染交给 Worker，GPU 若之后准备好，从下一次渲染起使用。
  - 自检不通过（见下）。
- **启动自检**：
  - 精度靠的是编译器不化简误差项（见下）。这一点只在本机（Chrome，Metal）上验证过，其他平台的编译器未必如此。一旦误差项被化简，GPU 会画出错误的图，而且不报任何错。所以启动时先用真实的着色器、缓冲区和读回算一个小例子。
  - 例子是实轴上尖点 1/4 右侧的 16 个点，c = 1/4 + (k + 8.5)·2^-28。参考点取 c = 0（轨道恒为 0），所以着色器实际迭代的就是 z 本身。
  - 这些点要 1–1.8 万步才逃逸。只用 f32 时，既存不下 c 的低位，也跟不上 z 越过 1/2 时的缓慢漂移，所以只要有误差项被化简，逃逸步数就会差出几千步，或者根本不逃逸。
  - 结果与 JS 双精度逐点比较，每点相差超过 1 次迭代即判定不通过。
  - 自检约 20–30 ms；适配器、设备和管线的初始化约 100–150 ms，自检前后都有。
- 渲染过程中出错时也改由 Worker 渲染（见“大画布与出错”）。

在无界面 Chrome 中逐一注入以下情况（都不带 `?gpu`），画面都完整画出：

- 没有 WebGPU、适配器为空、软件适配器、申请设备失败、适配器一直不返回（等 2 秒）、着色器无效、误差项被化简（模拟编译器化简：把误差项替换为 0，自检发现）。
- 设备在自检后、渲染中途、一开始就被销毁，以及读回失败。

**精度：用两个 f32 拼成一个数（double-single）**：WGSL 没有 64 位浮点，所以每个数用一对 f32（高位加低位）表示，约 48 位有效数字。

- 拼接时要用到舍入误差项。按通常的写法 (a + b) - a，Metal 的着色器编译器会把它化简成 0；现在所有误差项都改用 fma 对一个运行时读入的 1 来计算，编译器无从化简。
- 实测中，通常写法的误差项恒为 0，fma 写法给出的误差与 CPU 双精度算出的完全一致。
- 只用 f32 时，细丝多的视图里有 6–7% 的像素颜色明显不同，现在只有 0.1–0.8%。

**扰动迭代**：

- 每个像素以 δ′ = (2Z + δ)·δ + δc 跟踪自己与参考轨道 Z 的差；|z| < |δ| 时换回参考轨道起点，并同时计算距离估计。没有 BLA。
- 参考轨道就是 Worker 共用的那条：0 号 Worker 在后台算好后，主线程转发给 GPU，视图中心相对参考点的偏移加进 δc 里。主线程不再自己用 BigInt 计算轨道；只有浅层视图（Worker 不用参考轨道）才在主线程算一条。

**流程**：

1. **粗阶段**：每块只算每 4 个像素中的一个（每个方向），按 Worker 粗阶段的方式画成小块。
   - 在 GPU 上重算这些采样很便宜，所以与 Worker 粗阶段对待“便宜的未定采样”的方式一样：只要 `adaptBudget` 认为该提高，就立即提高预算。计入的采样是未定的加上疑似内部的。
   - 只采纳“提高”，不采纳“饱和”（提高不再明显减少未定采样，此后不再提高）。GPU 分不清边界附近的内部像素和逃逸很晚的像素，视图以内部为主时，未定比例会一直降得很慢。
     - 原来据此判定饱和，结果挡住了后面 Worker 证明之后本该进行的提高。例如 `0.3231068534708 + 0.5529136600610i`、`4.742×10^6`（周期 4 泡的边缘）停在 24576 次：未定比例从 93% 只降到 72%，但证明之后真正未定的有 8%。纯 CPU 渲染则提高到 98304。
     - 结果是这个泡的边界外有 4.3% 的像素被画成黑色，黑色区域明显偏大，伸出的细丝也短了一截。现在两者都到 98304。
   - 每次提高只重算这些采样，排成列表来算（见下面“把跑得久的像素集中起来算”）。
2. **其余像素**：
   - 主心形和周期 2 泡里的像素，以及四角的粗采样都被 GPU 当作内部的 4×4 块里的像素，不在 GPU 上算，在精细阶段开始前直接交给 Worker（见下面“内部块和浅层视图交给 Worker”）。前者在粗阶段之前就判出，粗阶段也不算。
   - 预算达到 32768 时（浅层视图从 8192 起），先用较低的上限算完，未定的像素再按完整预算排成列表重算（同见下面）；浅层视图则把它们直接交给 Worker。
   - 已逃逸的像素直接作为最终结果（质量 1）。
   - 其余像素交给 Worker，之后由 Worker 的结果替换。这包括当作内部、疑似内部（判定方法见下）、仍未定的像素，以及疑似抵消的像素：|z|² < |Z|²·10⁻¹¹，δ 已损失约 18 位。
   - 其中当作内部的先画成黑色（质量 2）；其余（未定、疑似内部、疑似抵消）先不画，保留下面放大的旧图，粗阶段的这类采样也一样。原来都先画成黑色：深层视图里很多像素要几万步才逃逸，缩放时画面会整片变黑，再被 Worker 一点点画出来（见下面“缩放和拖动过程中只做预览”）。
3. **交给 Worker**：剩下的像素按块由近到远、块内逐行，每 32 个一段（像素少时段更短，让每个 Worker 都分到）轮流分给各 Worker，用与 CPU 渲染相同的采样器精确计算：证明内部像素，必要时退回 BigInt。浅层视图里同一行的像素一起交给 `directRow`，与 CPU 渲染一样逐行证明内部。算完后直接替换，并报告哪些仍未定。
   - 不等精细阶段算完：每攒够每个 Worker 1024 个像素就发出一批，Worker 在 GPU 继续计算的同时证明内部像素，同一次渲染的各批按顺序处理。原来要等 GPU 算完整幅才开始，两段时间相加。
     - 例：`0.3231068534708 + 0.5529136600610i`、`4.742×10^6`（1874×1516，M4 Mac mini），GPU 精细阶段约 17 s，Worker 证明约 12 s。原来先后进行共 30.6 s，同时进行后 18.5 s。
   - 这些都是昂贵的像素，所以深层视图按像素数的 32 倍、浅层视图按 2048 倍来决定 Worker 数，几千个（浅层几百个）像素也会用上所有 Worker。例如 `0.354939198463346 + 0.640822400737588i`、`1.7×10^9` 在 640×257 下，只用 1 个 Worker 要 5.2 s，用满 8 个是 2.0 s。分批发送时事先不知道会剩多少，按本轮要计算的像素数估计。
4. **提高预算**：由 Worker 证明之后仍未定的像素来决定，规则与 Worker 初稿之后的相同（`adaptBudget`，超过 0.01% 即提高）。
   - 需要提高时，GPU 按新预算把这些像素排成列表重算，仍定不下来的再交给 Worker。浅层视图不经过 GPU，直接交给 Worker。
   - 所有像素在新预算下都完成之前，画面仍记为原预算，与 Worker 加深时相同。这期间平移会按新预算整幅重画，不会把还在等待的黑色像素当作已完成的结果复用。
   - GPU 自己分不清边界附近的内部像素和只是需要更多迭代的外部像素，Worker 的证明分得清，所以预算的走向与纯 CPU 渲染一致。
5. **平移**：已完成的像素照常复用，只计算其余像素，不做粗阶段。平移后若需要提高预算，则整幅按新预算重画，原因与 CPU 路径相同。

**分批显示，不卡主线程**：

- GPU 以 64 像素的块为单位，从画布中心向外计算。每批只算几块，每批 GPU 时间约 12 ms；同时有 3 批排队，读回一批时，GPU 已在算下一批。
- 每批至少 4096 个采样（粗阶段 16 块，精细阶段 1 块）。只算掩码内像素的阶段（平移后新露出的像素）按要算的采样数凑批，每批最多 64 块；列表每批最多 65536 个像素。
  - 一批的耗时大致等于其中最慢像素的迭代次数，直到 GPU 被占满为止。在 98304 次迭代下，粗阶段一批 1 块（256 个采样）要 80–99 ms，16 块也只要 120 ms。
  - 原来按耗时把批缩到 1 块后就再也不会增大：1874×1516 的画布上，以内部为主的视图粗阶段要约一分钟，现在约 6 s。
- 每批读回后立即画出，所以画面和 CPU 渲染一样先粗后细、由中心向外出现。
- 主线程每批最多处理 65536 个像素，每处理约 8 ms 就让出一次事件循环。
- 交给 Worker 的像素在每块画出时顺手记下并分批发出（见上），不必最后再扫描整个画布。

改成这样之前，GPU 模式会一次处理整幅 250 万像素的结果（着色、计算掩码、排序剩余像素），主线程每次卡 60–160 ms，帧间隔最长 150 ms。改后在同样的高负载下（load average 约 55），长任务不超过 68 ms，大多数时候一个也没有，最长帧间隔与 CPU 模式相当。

**缩放和拖动过程中只做预览**：

- 视图连续变化时，GPU 只算粗阶段（拖动时只算新露出的像素），迭代上限压到 4096：每批约 4 ms，不提高预算，也不交给 Worker。预览不算完成，停下后再按完整预算渲染。
- 到上限仍未逃逸的采样不画，保留放大的旧图。原来画成黑色：`-0.580664321513791016485221029573 + 0.651798114898003455891331802941i`、`5.92×10^23`（预算 57344）继续放大时，画面有约 0.3 s 80–100% 是黑的；细丝很多的 `1.93×10^10` 也一样。CPU 模式一直是先放大旧图再替换，最暗时约 9%。现在两者相同（无界面 Chrome 里滚轮连续放大，按画面中近黑像素的比例测）。
- 原来变化过程中也按完整预算渲染。在以内部为主、预算很高的视图里，一批就要约 100 ms，粗阶段一轮做不完就被下一次变化打断，画面只是旧图不断放大变糊，停下后才突然变清晰。
  - 例：从 `0.3231068534708 + 0.5529136600610i`、`1e4` 开始按住 `+` 6 秒（1874×1516，预算 98304）。原来只上传了 12 次新像素，最长 2.7 s 没有更新，帧间隔最长 250 ms，一轮粗阶段也没完成。
  - 现在完成 29 次预览，画面最长约 250 ms（第一次）更新一次，帧率保持 60。
- 深层视图的共享参考轨道仍按完整预算计算（在 Worker 里），停下后的完整渲染直接复用；浅层视图在主线程临时算的轨道只算到预览上限。

**大画布与出错**：

- 结果缓冲只够 3 批（每批最多 64 块的采样，6 MiB）轮流使用，掩码每像素 1 字节，并按适配器的上限申请缓冲大小。
  - 原来按块数分配结果缓冲，约 1700 万像素（如 6016×3384）以上会超过 128 MiB 的绑定上限。缓冲因此无效，读回全是 0，整幅被当作“已逃逸”画成同一种颜色，并标为完成。
  - 现在 6016×3098 也能正常完成。
- GPU 出错时，改由 Worker 渲染，之后一直如此。出错包括设备丢失、读回失败、校验错误（`uncapturederror`）。
  - 原来渲染会停在半途，一直标着未完成，点击也不会重来。
- 0 号 Worker 只为 GPU 算参考轨道时，不发送采样。每一轮交给 Worker 的任务带轮次号，过时的消息直接丢弃。
  - 原来这次空的“完成”消息会被当成一个 Worker 的报告，这一轮提前结束，之后到达的像素被丢掉。最多有几百个像素一直没画；只有 1 个 Worker 时，所有这些像素都没画。

**提前判定为内部**：每 16 步检查一次，轨道是否回到上一个 2 的幂次步时的位置附近（|Δz|² < 10⁻¹⁴）。回到附近时，再看两个条件：

- **dz/dc 已经稳定**：log2 的增长不到 0.01。
- **轨道在收缩**：从那一步到现在，|2z| 的乘积（即这段轨道的导数）小于 1/8。

两个条件都满足后，还要再迭代到当时步数的 4 倍仍未逃逸，才当作内部，不再跑完整个预算；若在此之前已到预算，就标为疑似内部。这不是证明，所以这些像素仍交给 Worker 证明。

- **为什么要 dz/dc 稳定**：在海马谷深处，逃逸的轨道会在一个弱排斥周期旁徘徊上千步，位置在 3×10⁻⁶ 以内重复，dz/dc 的增长也不到 2 倍。只看位置时，那幅视图几乎全部被误判成内部。
- **为什么要轨道收缩**：只看位置和 dz/dc 时，`0.354939198463346 + 0.640822400737588i`、`1.7×10^9` 这类视图里，有些逃逸的轨道沿着一个接近抛物型的周期缓慢移动，位置和 dz/dc 都几乎不变。640×257 下有 7315 个这样的像素被当作内部，先画成黑色，要等 Worker 一块块算到才变回彩色，所以初始画面会出现边缘平直的大块黑色。
  - 吸引周期上这段轨道会收缩，接近抛物型的周期上则不会。
  - 收缩阈值的测试结果：1/2 时仍误判 594 个像素，1/4 时 31 个，1/8 时 2 个，1/16 时 0 个。阈值越严，提前认出的内部像素越少（1/8 时认出 23517 个内部像素中的 13240 个），其余内部像素由 Worker 证明，与纯 CPU 渲染相同。
- **为什么还要多迭代到 4 倍步数**：靠近实轴时（例如 `-1.8541330553638606402648 + 7.2361×10^-18 i`、`1.4×10^16`），轨道会先跟着附近一个实参数的吸引周期走一段：位置重复、dz/dc 稳定、轨道收缩，三个条件都满足。之后虚部慢慢长大，轨道离开并逃逸。
  - 640×257 下有 6612 个这样的像素被当作内部，先画成黑色，等 Worker 一块块纠正，画面上出现大块黑斑和竖直的块边。
  - 它们在第 990 步左右被认出，在 1.6–2.6 倍步数时逃逸。多迭代到 2 倍仍会误判 3365 个，到 4 倍为 0。
  - 那个视图的整幅渲染从 7.5 s 降到 0.7 s：Worker 不必再纠正这些像素。
  - 代价：全是内部的视图，GPU 计算从 3 ms 变成 19 ms（640×257），在 Worker 证明内部像素的时间面前可以忽略。
- **疑似内部**：回到过附近但没通过上面两个条件、又在预算内未逃逸的像素，标为疑似内部，不在 GPU 上反复提高预算重算，直接交给 Worker。它们大多是边界附近的内部像素，Worker 的证明比 GPU 继续迭代快得多。

**吸引周期较长时更早交出（GPU 上的多步 Newton 法）**：上面的测试要求回到 10⁻⁷ 以内，并迭代到 4 倍步数。吸引周期长、收缩又慢时，这要几万步：`0.3231068534708 + 0.5529136600610i`、`4.742×10^6` 的内部像素周期为 512–1024 步，周期的乘子 |λ| 多在 0.9 以上（抽查 8 个像素为 0.91–0.99），轨道靠近得很慢，大多数像素跑满预算（3.2 万到 13 万次）才交给 Worker。Worker 不等轨道靠近，在粗略回归时就用 Newton 法直接求周期点（见“吸引周期”）。GPU 上做同样的事，只是不作证明，只为尽早把像素交给 Worker：

- 从第 128 步起记一个基点 b：|z| 最小处，每到 2 的幂次步也重记一次。并记下从 b 到当前的导数 λ（复数，f32）。
- 从第 256 步起，轨道回到 b 附近时（|z|² 与 |b|² 相差不到 |b|² 的 1/4，且 |z − b|² < |b|²/4），设周期 P 为这段步数，从 w = z 开始对 f^P(w) = w 做 Newton 迭代：
  - 真实轨道的状态先存起来。每一步 Newton 是从 w 出发的一圈 P 步：把 w 当作换回参考轨道起点后的 δ，用同一段扰动代码迭代，同时累乘 λ = (f^P)′(w)，然后 w ← w − (f^P(w) − w)/(λ − 1)。
  - 步长小于 |w| 的 2^-12，且 |λ|² < 1 − 2^-10 时，当作内部交给 Worker 证明。这个余量是为了启动自检：那 16 个点旁的不动点接近抛物型，|λ| 只比 1 大一点，f32 的舍入不能把它算成吸引的。
  - 否则（收敛到排斥周期、三圈后步长不再缩小、圈数用完、中途逃逸或抵消）回到存下的轨道接着迭代，第 k 次失败后要再过 4P·2^k 步才再试。
  - 每次最多 10 圈。一个像素所有 Newton 圈加起来不超过预算的 1/4。回归间隔 P 可能长达几万步（基点在 2 的幂次步重记），不设上限时，131072 次预算下有像素多走了 25 万步。一批的耗时取决于其中最慢的像素，这会拖慢整批。
- **相邻采样的提示**：粗采样点用 Newton 认出内部后，把周期点和周期记在它的 4×4 块上。精细阶段的像素若所在块和右边、下边的块记着同样的周期，就先从这个周期点开始做至多 3 圈 Newton，成功则完全不必迭代自己的轨道；不成功就从头正常迭代。
- 误判只影响速度：这些像素交给 Worker 后仍被精确计算。带 Newton 的内核也要通过启动自检，不通过就只用普通内核。
- 双精度模拟（每 48 像素取一个，预算 131072），每像素的 GPU 平均步数如下。两个视图中，被当作内部、最终却逃逸的都是 0 个。

  | 视图 | 原来的周期回归测试 | Newton | Newton 加提示 |
  | --- | --- | --- | --- |
  | `0.3231068534708 + 0.5529136600610i`，`4.742×10^6` | 20657 | 13619 | 约 8000 |
  | 海马谷 `-0.7436438870371587 + 0.1318259042053119i`，`10^7` | 6104 | 2720 | 约 2000 |

- 在 GPU 上实测精细阶段的总步数：第一个视图从 487 亿降到 212 亿，海马谷从 143 亿降到 48 亿。但完成时间几乎不变，原因见下一段。

**把跑得久的像素集中起来算**：

- GPU 上同一个 SIMD 组的线程（M4 上 32 个）同步推进，原来一组是一块里相邻的像素。少数跑满预算的像素散在各组里，各组就要陪着这一个像素跑完，其余线程空等。
  - 第一个视图里，4.6% 的像素走了超过 32768 步，占精细阶段总步数的 55%；海马谷 `10^7` 里是 0.9% 的像素占 42%。Newton 省下的主要是其余像素的步数，所以时间没变。
- 所以需要跑很久的像素改成列表来算：每个线程从列表里取一个像素，每 64 个像素一组。用于三个地方：
  - 粗阶段提高预算后的重算：只剩未定的采样，稀疏而且都要跑很久；
  - 精细阶段延后的像素（见下）；
  - Worker 报告未定、提高预算后的重算。
- **精细阶段先设上限**：预算达到 32768 时，精细阶段先只算到一个上限，这时未定的像素记下来，不交给 Worker，等这一阶段结束后按完整预算排成列表重算。
  - 上限取粗采样中 90% 的采样所用的步数，至少为预算的 1/8；超过预算一半就不设上限。未逃逸的采样把所用步数（含 Newton 圈）写在距离的位置上，供这里统计。
  - 只用预算的 1/8：细丝很多的 `1.93×10^10`（预算 32768）里像素在 4000–8000 步之间逃逸，89% 的像素要重算一遍，从 4.4 s 变成 5.9 s。
  - 上限低于预算的 1/8（例如取 95% 分位数时，海马谷 `10^7` 的上限是 10220）：会有更多稍后就逃逸的像素进入列表，长短不一，列表又慢下来，从 5.0 s 变成 5.8 s。
- 一批的耗时仍取决于其中最慢的像素。加列表之前试过让精细阶段每批固定 16 块（不随耗时缩小），第一个视图的精细阶段从 15.9 s 降到 11.6 s，但每批要约 320 ms，GPU 长时间被占用，界面响应会变差，所以没有采用。

**内部块和浅层视图交给 Worker**：GPU 当作内部的像素只是猜测，都要由 Worker 再证明一次。在以内部为主的视图里，大部分像素因此被算了两遍，Worker 还要等 GPU 精细阶段一点点交出像素。浅层视图里 Worker 用普通双精度三路并行迭代，证明内部很便宜，于是这类视图的 GPU 模式反而比 CPU 模式慢 1.3–1.7 倍（全貌、周期 3 泡、象谷）。现在：

- **内部块直接交给 Worker**：一个 4×4 块四角的粗采样都是 GPU 当作内部的（不含未定、疑似内部：其中有不少是晚逃逸的细丝，GPU 算得快得多），块里的像素在精细阶段开始前就交给 Worker，精细阶段跳过它们。块里若有逃逸的像素，Worker 照样精确算出，只是慢一些。
  - 按块分批发出，每攒够约 65536 个像素发一次，每 8 ms 让出一次事件循环。一次全部发出时（周期 3 泡 `300` 倍有 230 万个像素），主线程会卡 53–66 ms。
- **主心形和周期 2 泡先在主线程判出**：GPU 开算之前，主线程按 Worker 的方式算出每个像素的 c（双精度），用与 Worker 相同的公式（`insideDouble`）判断是否在这两个区域里。是的像素当作内部，粗阶段和精细阶段都不算，直接交给 Worker，Worker 立即证明。
  - 原来 GPU 分不出它们：在抛物点（`-0.75`、`0.25`、`-1.25`）附近，这里的吸引周期 |λ| 接近 1，Newton 判不出收敛，像素被报成未定。粗阶段因此把预算从 1536 提高到 24576（纯 CPU 停在 1536），精细阶段又要在 GPU 上算 2–8 s，而 Worker 全部算完只要约 0.3 s。
  - 判错只影响速度：Worker 对交给它的每个像素都精确计算。每像素尺寸小于 2^-40 时不判：c 的双精度不足以区分相邻像素，整幅视图可能被当成内部。
  - 视图不碰到这两个区域（实部 −1.25 到 0.25，|虚部| ≤ 0.65）时直接跳过；整幅判断约 10 ms，分段让出事件循环。
- **成段分给 Worker**：原来逐个轮流分，8 个 Worker 各拿到每隔 8 个的像素。相邻像素的周期提示（见 `directRow`）接不上，浅层内部像素在 Worker 上的代价是成段时的 3–5 倍（单个 Worker 预热后测：每像素 1.9 µs 对 0.4–0.6 µs）。现在每 32 个一段。
- **浅层视图的 Worker 数**：最后一次提高预算时只剩几百个未定像素，每个都要跑满新预算，原来按像素数的 32 倍估计，全貌只用了 8 个中的 2 个。
- **浅层视图里定不下来的都交给 Worker**：精细阶段从 8192 的预算起就设上限，到上限仍未定的像素不再排成 GPU 列表，Worker 证明内部和算晚逃逸的像素都很便宜；Worker 报告未定、提高预算后也不经过 GPU。原来周期 3 泡 `300` 倍的预算为 24576，精细阶段不设上限，少数跑满预算的像素让精细阶段拖了约 650 ms，Worker 只能等。

只要着色器里有提前交出的代码，即使从不触发，几乎全是逃逸像素的视图也会慢 12–17%（细丝很多的 `1.93×10^10`，M4；当时是原来的周期回归测试），减少寄存器、改写退出方式都没有用。所以编译两个内核，按需选用：

- 带测试的内核在 GPU 可用之后才在后台编译和自检，好了之前一律用普通内核。启动时就编译并自检两个内核，第一次渲染要晚约 100 ms。
- 第一次粗阶段和预览用不带测试的内核。
- 粗阶段提高预算后的重算只涉及仍未定的采样，第一次用带测试的内核；之后只有它把超过 1% 的采样判为内部时才继续用。细丝视图在低预算下全部采样都未定，但它们之后都逃逸了，测试判不出内部，后面就换回普通内核。
- 精细阶段（及其延后的列表）在粗采样中有超过 1% 未逃逸（内部、疑似内部或未定）时用带测试的内核；平移时沿用上一次整幅渲染的选择，精细阶段的上限也一样。
- Worker 未定之后按更高预算的重算总是用带测试的内核。

| 全貌 | 0.8–0.9 s | 1.3 s |
| `0.354939198463346 + 0.640822400737588i`，`1.7×10^9` | 13.0 s | 14.0 s |

- 最后这个视图有约 23% 的像素是边界附近的内部像素，要由 Worker 证明，所以两种模式差不多。

在 M4 Mac mini 上（1874×1516 个物理像素，无界面 Chrome，负载很低）的完成时间，每格 3 次。“最初”是只有上面第一个提前判定时；“周期回归”是加上原来的周期回归测试、并让 Worker 边收边算之后；“现在”是 Newton 法、提示和列表：

| 视图 | 最初 GPU 模式 | 周期回归 | 现在 | CPU 模式 |
| --- | --- | --- | --- | --- |
| `0.3231068534708 + 0.5529136600610i`，`4.742×10^6`（以内部为主） | 37.1–37.8 s | 18.5–18.8 s | 13.4–13.5 s | 22.9 s |
| 海马谷 `-0.7436438870371587 + 0.1318259042053119i`，`10^7`（约 60% 内部） | 29.7–30.1 s | 9.4–9.8 s | 4.8–5.2 s | 6.1 s |
| 细丝很多的 `1.93×10^10` | 4.3–4.4 s | 4.4–4.5 s | 4.2 s | 11.9 s |
| 近实轴针状 `1.4×10^16` | 1.05–1.11 s | 0.99–1.08 s | 1.02–1.06 s | 3.7 s |
| 小芒德布罗特集旁 `5×10^4` | 0.62–0.64 s | 0.66–0.74 s | 0.62–0.66 s | 1.7 s |
| 海马谷 `1000` | 0.41 s | 0.44–0.53 s | 0.41–0.46 s | 0.93 s |

- 第一个视图里，只加周期回归测试时从 37.7 s 降到 30.6 s：粗阶段很快就把预算提高到 131072，但精细阶段仍要约 17 s，之后 Worker 再用约 12 s；两段同时进行后降到 18.5 s。
- 海马谷 `10^7` 的 GPU 模式现在比 CPU 模式快。只换成 Newton 法时，精细阶段的步数降到 1/3，完成时间却没变（约 9.8 s），要把跑满预算的像素排成列表单独算之后才降下来。
- 只换成 Newton 法时，海马谷 `10^7` 的粗阶段认出的内部像素多了，未定的采样不到 1%，预算停在 32768。Worker 证明之后有 0.75% 的像素未定，又要提高到 131072 重算。这时重算的像素按块分批，每块约 180 个像素，一批只放一块，118 批共 7.5 s。现在这类重算排成列表，掩码阶段也按要算的采样数凑批。
- 最后两行时间很短，表中完成时间是测试脚本每 100 ms 查一次完成标志得到的；海马谷 `1000` 的 GPU 时间为 253–285 ms，改前 260–304 ms。
- 全部是内部的视图没有加速：每个像素都要由 Worker 证明。
- 全貌附近的尖点总有少数像素未定，GPU 会把预算提得较高，Worker 也要在这个预算下证明内部像素，所以全貌加速有限。

**限制**：

- 结果与纯 CPU 渲染不逐位一致：约 0.1–0.8% 的像素颜色略有不同，而且结果与显卡有关。
- 不一致的地方不一定是 GPU 错：
  - 在每像素约 2^-37 的深度，Worker 原来用普通双精度直接迭代。迭代次数多时会偏差 0.004–0.2 次，上面那个视图约 3% 的像素颜色因此不同；抽查的 24 个像素中，GPU 的结果有 23 个与 BigInt 一致，Worker 的一个也没有。现在 Worker 从 2^-24 起就用扰动（见迭代路径）。
  - 海马谷视图里，有 122 个像素 BigInt 在 2300–2540 次逃逸，Worker（带 BLA 的扰动）到预算 2560 仍未定；GPU 没有 BLA，算对了 18 个抽查像素中的 17 个。BLA 的阈值已从 2^-36 收紧到 2^-40（见 BLA 一节）。
  - 这两点都是纯 CPU 渲染本身的精度问题，已经改进。
- Node 里没有 WebGPU，单元测试只用一个假设备检查分批调度（例如最后一批之后视图已变，计算会报告已停止；列表的每个像素恰好算一次；掩码阶段按要算的采样凑批），覆盖不到着色器本身。着色器在真实 GPU 上的检查见“测试”一节的 `npm run test:gpu`；以上数据来自无界面 Chrome 中的端到端脚本。
- 只服务到 2^-90：f32 的指数在 2^-126 以下就不够了。更深的视图需要给数值加独立指数，并在 GPU 上实现 BLA。
- 着色器编译会在页面打开时让主线程停顿一次（这台机器在高负载下约 0.45 s）。

### 迭代预算

预算按深度公式增长，并按实际情况自适应。在预算内既未逃逸、也未被证明为内部的像素称为“未定”，计算内核会逐个像素报告。

**先出初稿，再补算未定像素**：

1. 每次渲染先按当前预算画完全分辨率的初稿。未定像素暂时画成黑色。
2. 初稿完成后，若未定像素超过 0.01%，就只把这些像素按 4 倍预算重新计算，其余像素保持不变。
   - 各 Worker 在最终阶段报告自己分块里的未定像素。主线程把它们合并，按分块离中心由近到远排好，同一分块的像素放在一起，再以 32 个为一段轮流分给各 Worker。这与 GPU 模式把像素交给 Worker 是同一条路：结果以采样带回，由主线程着色。
   - 原来每个 Worker 只补算自己分块里的未定像素。内部区域常常集中在画面一侧，分到多的 Worker 要比别的晚很久才算完：`4.17×10^13`（1280×800，2 倍像素密度）两次补算中，最快和最慢的 Worker 相差 3.0 s 和 9.3 s。平均分配后只差不到 0.6 s，整个视图从约 60 s 降到约 56.5 s（新旧各测两次）。
   - 不共享参考表时，更高的预算可能只容得下更少的 Worker（每个 Worker 都存一份参考表），补算就只分给这些 Worker，不必整张重画。
   - 未定像素画成黑色，可能是错的；而提高预算只重算它们，所以这里的门槛远低于粗阶段的 1%。
   - 原来也是 1%：海马谷 `1.9×10^12` 的视图在 640×257 下有 0.96%（1571 个像素）停在 2560 次迭代、画成黑色，其实它们全部在 10240 次以内逃逸。改为 0.1% 后，`-0.745+0.113i`、`1000` 在 640×400 下仍有 0.09%（228 个）停在 1536，其中只有 12 个到 6144 还未逃逸。
3. 重复第 2 步，直到提高预算不再明显减少未定像素，或达到深度公式的 64 倍（限定在 2^16 到 2^20 之间）。

补算后的画面与直接用最终预算渲染的结果逐位相同。以下情况仍整张重画：

- 粗阶段就有超过 25% 的采样未定：这样的初稿大半是占位的黑色，先画出来没有意义，于是在画全分辨率之前就提高预算。
- 粗阶段的未定采样很便宜：各 Worker 报告每个阶段的采样耗时，以及其中花在未定采样上的部分。若后者不超过 10%（例如 BLA 让这些像素跳过了绝大部分迭代），按 4 倍预算重算它们最多让后续阶段多花约 30%，于是同样在画全分辨率之前就提高预算。否则初稿里的黑色占位块要等整幅初稿完成才会补上：例如 `#re=-0.7436438870371700355&im=0.1318259042052868754&zoom=1.906544542e12` 中心约 1.4% 的像素需要 2560 次以上的迭代，原来要黑着等完整个初稿（Mac mini 上 2.35 秒，本身补算只要 0.08 秒），现在零点几秒后就开始以正确的颜色出现。未定采样很贵时（例如抛物点附近），仍先出初稿，这正是“先出初稿”快 1.8–4 倍的情形。
- 这次渲染是平移，只计算了新露出的部分：复用过来的像素仍停在旧预算，只补算新算的部分会让画面不一致。

学到的预算在附近继续沿用；缩小超过 8 个二进制量级，或重置视图后，恢复按公式计算。

例如海马谷约 10^15 倍处，按公式的 2560 次迭代整幅画面都是黑的，实际像素需要数千到数万次迭代。

在 Mac mini（M4）上以 8 个 Worker 渲染 640×400，与原先“粗阶段超过 1% 未定就重来”的做法相比：

| 视图 | 第一张完整画面 | 完成 |
| --- | --- | --- |
| 13/30 分支根部 `1.8×10^8` | 7.0 s → 3.6 s | 7.0 s → 5.7 s |
| `4.17×10^13` | 5.8 s → 1.8 s | 5.8 s → 4.5 s |
| `1.83×10^12` | 1.5 s → 0.4 s | 1.5 s → 0.8 s |
| 海马谷 `10^15` | 2.7 s → 1.6 s | 2.7 s → 1.9 s |

0.25 尖点旁那类几乎每个像素都要十几万次迭代的视图没有变化：粗阶段每次都有七成以上未定，仍按原方式先提高预算。

### 局限

源码没有固定的放大倍数上限，但计算量受 CPU、内存和迭代预算限制，不能保证任意区域、任意深度都实时完成高清重绘。

黑色表示已被证明在集合内部，或在当前预算内尚未逃逸；后者不是严格的集合归属证明。

## 配色

### 复刻原动画

配色复刻维基百科 Mandelbrot set 条目中的动画 [`Mandelbrot_sequence_new.gif`](https://en.wikipedia.org/wiki/Mandelbrot_set#/media/File:Mandelbrot_sequence_new.gif)，由动画全部 475 帧反推得到。

- **视图**：每帧都以海马谷的同一目标点为中心，按 1.1495 倍等比放大，共约 4×10^28 倍。拟合时不依赖配色：按算出的逃逸次数给像素排序，相邻像素颜色变化最小的视图即为该帧视图。
- **映射**：只用没有混色的平坦像素，共约 300 万个样本，配对颜色与逃逸次数 n。各帧在同一 n 上的颜色只差 0–3 个色阶，说明颜色只是 n 的函数：渐变位置为 `frac(√(n + 4) / 32)`。
- **渐变**：正是生成器 [`MandelAnimator.java`](https://github.com/josch/mandelbrot_zomb/blob/master/src/deepZoom/MandelAnimator.java) 中的 10 个色标（深蓝紫、宝蓝、浅青、近白、金黄、橙、赭红、暗紫……），均匀分布在一圈上，用周期 Hermite 样条连接。与实测渐变平均相差 1.7 个色阶，接近 GIF 自身的量化误差。

### 深层的调整

**第一圈（n < 1020）与动画完全一致**，之后有三处调整。

**对数节奏**：原动画的每一圈随 √n 越拉越长。在许多位置，逃逸次数随放大增长得很慢，整个画面都落在一圈中的一小段里，几乎只剩一种颜色。

- 第一圈之后，变化速率在 n = 1020–1500 间平滑过渡到对数节奏：逃逸次数每增加约 28% 走完一圈。
- 于是放大时各种颜色会依次循环出现，而同一个点放大前后颜色不变。

**更快经过暗色段**：渐变中从赭红经暗紫到宝蓝约四分之一都很暗，深层画面若正好落在这一段就几乎全黑。从第二圈起，这一段以 3 倍速度经过，只作为赭红与蓝色之间的点缀。

**距离估计勾勒边界**：任何固定的“逃逸次数 → 颜色”映射，都会让某些画面落在对比度很低的一段（例如浅青到近白），细丝融进背景。

- 迭代时同时计算导数 z′ = dz/dc，逃逸时得到每个像素到集合边界的距离估计 |z|·ln|z| / |z′|。
- 距边界半个物理像素以内的像素逐渐压暗，紧贴边界处最多压暗 65%。三个通道等比例缩放，色相不变。
- 距离来自每个像素自身的导数，所以轮廓平滑，不受相邻像素噪声影响，在任何深度、任何渲染阶段都一样。
- 导数以“每像素”为单位跟踪，在普通指数范围内不会溢出；BLA 跳步对导数同样是线性映射。

集合内部为黑色。颜色只取决于逃逸次数和边界距离，与平移和迭代预算无关，所以已有像素可以直接复用。

### 鲜艳配色

第二套配色取自 Maths Town 的缩放视频 “Eye of the Universe - Mandelbrot Fractal Zoom (e1091)” 前四分钟的画面：颜色是逐帧实测出来的，而不是照着感觉调的。

- **观察**：视频里每个像素的颜色同样只由逃逸次数决定。把不同帧里逃逸次数相同的平坦像素放在一起比较，颜色只差 2–17 个 RGB 级（中位数）。但它的色板和经典配色的结构不同：几百次以内是缓慢的渐变（长春花蓝、近白辉光、青、近黑、酒红、玫瑰……），之后颜色按逃逸次数本身而不是它的对数前进，大约每 200–250 次就有一亮一暗两条色带，每一对都换一个色相（青、绿、绯红、金、紫、蓝、橄榄、玫瑰……），在测到的范围内没有重复。
- **实测**：先把视频的各帧配准到复平面上，也就是找出每帧对应的视图：
  - 前半分钟按集合轮廓和逃逸次数对齐；
  - 更深的帧按画面边缘与我们算出的逃逸次数的边缘对齐，这种对齐与配色无关；
  - 视频每秒放大约 1.81 倍，中心收敛到 0.3602404434 + 0.6413130611i（与 0.36024… − 0.64131…i 互为镜像）。

  然后在每帧里取附近没有细丝的平坦像素，按本项目的逃逸次数分成很窄的档（深处每 0.5% 一档），取各帧颜色的中位数，从全貌（n ≈ 0.5）一直测到 n ≈ 13900（视频第 240 秒）。在颜色近似线性变化的地方省略中间点（OKLab 误差 0.012 以内），剩下 511 个关键色，存在 `src/render/vivid-keys.ts`。关键色之间沿 log(n + 4) 在 OKLab 空间插值，按每 1/4 次逃逸一项建成色表。
- **测到的范围之外**：n 超过 13917 后，重复 n = 5497.5 起的一段，周期 8419.7 次。最后 120 次逐渐过渡到早一个周期的颜色，所以接缝处是连续的。这个起点是在实测数据里找的：在这里两段颜色最接近，OKLab 平均只差 0.06。
- **为什么这样做**：
  - 上一版只有开头（n < 400）是实测的，之后是 20 个色系的循环，与经典配色共用对数刻度，每 e 倍逃逸次数约 6 个色系。深处逃逸次数到了几千、几万时，一屏内的逃逸次数只差几百，在对数刻度上不到一个色系的几分之一，于是整屏是同一种颜色，常常是大片灰绿。
  - 按逃逸次数本身前进的色板则不管多深，一屏内差几百次就有几条不同色相的色带，这正是视频深处色彩丰富的原因。测试里会检查：在任意深度，跨 300 次逃逸的范围内总有一条暗带和一条亮带。
- **不加描边**：视频里的细丝没有描边，开头集合周围是发亮的辉光，所以这套配色不用边界距离。
- **切换配色不必重算**：颜色只取决于每个像素的逃逸次数和边界距离，配色只是映射。所以每个分块（包括粗阶段的）都把每个采样的这两个值随颜色一起带回主线程，按与颜色相同的方式铺到像素上保存（逃逸次数用单精度浮点，距离只在半像素以内才影响颜色，存成 0–254 的一个字节；每像素共 5 字节，平移时随像素一起移动）。切换配色时：
  - 已画出的像素（无论是最终像素还是粗阶段的块）直接用保存的值重新着色：约 290 万像素在 Mac mini 上只要 35–50 ms，第一次切换另需约 50 ms 建色表。
  - 正在进行的渲染不重新开始：各 Worker 收到新配色后，此后开始的分块就用它着色，粗阶段沿用的采样也按新配色重新着色；在 Worker 得知之前已按旧配色着色的分块，到达主线程时按其采样重新着色；之后的补算也用新配色。
  - 只有缩放时投影出来的旧画面预览没有采样，保持原样并标记为待画，由接下来的各阶段直接覆盖。
  - Worker 也按保存下来的值着色，所以重新着色与直接用新配色渲染的结果逐位相同。

```text
    dialog.ts            两个对话框共用的行为：点背景关闭、文本框随内容增高、复制按钮
    share-dialog.ts      分享对话框：短链接与完整链接
    short-link.ts        调用 is.gd 生成短链接（缓存、超时、限流与失败的原因）
    view-form.ts         解析视图对话框中输入的坐标与倍率
    hold-zoom.ts         可按住持续缩放的按钮（指针、按钮上的 Enter/空格、+/- 快捷键共用）
    view-info.ts         坐标与倍率的格式化
    url-state.ts         视图与 URL hash 的互相转换
    palette-menu.ts      配色菜单（点击、悬停与键盘操作）
    gestures.ts          滚轮与指针手势
tests/                   node:test 测试，文件名对应被测模块（input.test.mjs 用模拟 DOM 测试 main.ts）
scripts/                 性能基准、真实 GPU 检查（gpu-check.mjs）与图标生成
```

算法主要参考 Claude Heiland-Allen 的 [Deep Zoom](https://mathr.co.uk/web/deep-zoom.html) 与 [Deep zoom theory and practice](https://mathr.co.uk/blog/2021-05-14_deep_zoom_theory_and_practice.html)。

## 测试

需要 Node.js 22.18+（建议 24+）：

```sh
npm test
npm run build
```

**交互**：鼠标锚点、画布外缩放、连续 3000 次缩放、深层拖拽、双指缩放与平移、触点取消、任务取消、渐进覆盖和乱序结果保护；缩放按钮的过渡动画（单击无跳变、按住匀速、松开减速）与键盘操作；视图对话框的复制、应用（未改动的值保持精确）和无效输入的拒绝；分享对话框的完整链接、短链接与复制，is.gd 失败时的提示，以及过期回应的丢弃。

**短链接**（`short-link.ts`，用模拟的 `fetch`）：请求格式、缓存与并发请求合并、本机与局域网地址不发送、5,000 字符上限、限流暂停、失败可重试、超时，以及不是 is.gd 链接的回应会被拒绝。

**数值**：以多出 64 位精度的 BigInt 直接迭代为对照，覆盖非实轴的复杂边界和每像素 2^-2000（约 10^-602）的尺度。混沌边界按 10^-3 像素位移内精确值本身的变化范围比较。

**一致性与证明**：

- 三路交错与逐像素结果逐位一致；粗采样复用后的图像与逐像素采样相同。
- 内部证明（包括吸引周期与相邻提示）在 4 倍预算的 BigInt 迭代下无一逃逸。
- 相邻提示的结果与像素处理顺序无关。
- 距离估计与高精度导数一致；迭代预算的提高、停止与遗忘符合预期。

这些测试验证的是选定的测试点，并不构成对所有深度和边界的数学证明。

**真实 GPU**：Node 里没有 WebGPU，`npm test` 不会执行着色器。下面的命令会启动自己的 Vite 服务器，用无界面 Chrome 在本机 GPU 上实际渲染，每项检查用一个新的浏览器上下文：

```sh
npm run test:gpu                         # 约 30 秒
CHROME=/path/to/chrome npm run test:gpu  # 指定 Chrome
```

- GPU 通过启动自检，并实际用于渲染。
- 在 7 个视图上与只用 Worker（`?cpu`）的结果逐像素比较，其中周期 3 泡 `300` 倍是浅层、以内部为主的视图（几乎所有像素交给 Worker，见 GPU 渲染一节），`-0.75` 的颈部检查主心形和周期 2 泡里的像素在 GPU 开算前就交给 Worker。两者的预算各自按自己的未定像素提高，可能不同，所以不要求预算相同。
  - 只在 GPU 上是黑色、Worker 画出了颜色的像素，不超过 0.1%。预算停得太低时这个数会大很多：上面周期 4 泡边缘的问题，在这里是 3.4%。
  - 只在 GPU 上有颜色、Worker 画成黑色的像素必须确实逃逸。
    - 画布上分不清 Worker 的黑色是“已证明的内部”还是“预算用完仍未定”，所以抽查最多 24 个，用比视图多 64 位精度的 BigInt 迭代到 GPU 预算的 2 倍。内部点永远不会逃逸；混沌像素的精确逃逸次数可能略超出预算，所以允许最多 10% 的抽查不逃逸。
    - 本机实测：周期 4 泡边缘有 14 个这样的像素，全部确实逃逸。
    - 让着色器把判为内部的像素当作已逃逸（不再交给 Worker 证明），4 个视图失败，例如周期 4 泡边缘有 13397 个这样的像素，抽查 24 个只有 1 个确实逃逸。原来的比较完全不看这一类，会全部通过。
  - 渲染标记为完成后，结果要到下一个动画帧才画到可见画布上。所以读取前先等两帧，再隔两帧读一次，两次必须相同。
    - 不等待时，有的视图在完成那一刻还有 4797 个像素没更新。
  - 两边都有颜色的像素中，颜色明显不同的不超过 1%，这些是细丝中的混沌像素。其中一个视图要求不超过 0.1%，实际为 0。
  - 周期 4 泡边缘的视图放宽到 5%。它逃逸的像素极其混沌：像素中心只移动 10^-5 像素，精确的逃逸次数就相差约 1700 次（中位数）。在这样的像素上，GPU 和 Worker 落在精确值变化范围内的比例相同（抽查 30 个，各 24 个），谁也不比谁更准。
  - 本机实测：只在 GPU 上是黑色的为 0；颜色不同的为 0–0.25%，周期 4 泡边缘为 2.7%。
  - 把着色器里虚部的符号改反（自检只用实轴上的点，查不出），4 个视图都有 82–99% 的像素不同，检查失败。
- 没有 WebGPU、误差项被编译器化简（模拟）、渲染中途设备丢失时，画面都由 Worker 完整画出。

它只检查本机的 GPU 和浏览器。其他平台（Windows、Safari、手机）要在那里打开页面，与加 `?cpu` 的结果对比；画布的 `data-gpu` 为 `true` 表示用了 GPU，自检不通过时控制台会有警告。

## 性能基准

```sh
npm run bench               # 单线程：五个固定视图，各采样 160×100 像素
npm run bench:workers       # 真实 Worker 与完整渐进过程（384×240，不含浏览器绘制）
npm run bench:workers -- 2 4 8   # 指定线程数（1–8）
```

`bench` 报告三轮的中位数、参考轨道准备耗时和像素校验和；传入另一份 `src` 目录的路径即可比较两份实现。

2026-11-06 在 Apple M1 Max 上，以 8 个 Worker 渲染 1280×800 整帧（含全部阶段），最近一轮优化前后的对比（测试时机器负载较高，绝对值偏大）：

| 视图 | 优化前 | 优化后 |
| --- | --- | --- |
| `1.50×10^47` | 0.80 s | 0.44 s |
| `1.37×10^107` | 2.98 s | 1.80 s |
| 海马谷 `10^15`（预算 10240） | 11.6 s | 8.6 s |
| 含大块内部的 `4.17×10^13`（预算 40960） | 30.2 s | 11.0 s |

实际耗时取决于设备、位置和负载。

### 评估过但未采用

- **GPU 单精度预览**：只用 f32 时，细丝多的视图约 3.5–7% 的像素颜色明显不对，CPU 结果逐块替换预览时，画面会有割裂感。改用 double-single 后，GPU 结果可以直接作为最终结果（见 GPU 渲染）。
- **放宽 BLA 阈值**（2^-32 至 2^-24）：执行步数能减半，但从 2^-28 起就有像素超出精确值本身的变化范围；2^-32 在含大块内部的视图中反而更慢。
- **交错推进两个扰动像素**：结果逐位一致，但在 V8 中状态交接和寄存器压力的开销超过了收益。
